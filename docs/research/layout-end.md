# What was left of the editor's hand-built nodes after G-88

Researched 2026-11-14 for issue #100 (G-89), asked by bevy_dark_factory (the Cauldron), #260 (UI-99), tracking #208. After the editor adopted G-84 to G-88 its raw `Node` literals and hand patches went from 230 to 80; what was left that gooey can solve is here. Each item is a general need; the editor is the example and its name is in no API.

## Method

The rules of G-84 (`docs/research/layout-gaps.md`) stand: a layout choice is data on the node, never a literal in the host and never a number in `apply_skin`; the constructor or component puts it on the node and `apply_skin` writes the `Node`, so it follows the skin and the player's text size. G-84's review added one: **every field is an `Option`, and a field left `None` leaves the node alone** (`RowLayout`), so a component sets only what it names and never resets what a role or a host gave. Components that set a size, a space or a shape go on any node with a `Role`; where a unit is needed it is the skin's own (a step of `GooeySkin::spacing`, a multiple of the line weight `GooeySkin::border`, a step of `GooeySkin::radii`). Pointer defaults are documented on each constructor (a mark or a gap is `Pickable::IGNORE` like `screen()`).

## Items
1. **A node that starts closed: `Shown::closed()`, `ShownFollow::closed()`.** A bundle cannot say `Display::None` for a node whose `Node` another constructor wrote, and `Shown` only wrote it at the next restyle, so a node spawned after a frame's style pass was laid out open for a frame. `Shown` now has an `on_insert` hook that closes (or opens) the node **at insertion**: `Display::None` and `Visibility::Hidden` immediately, with the display and visibility it had remembered in `ShownMemory` (so opening restores them); `apply_skin` writes the same afterwards and finds it done. `Shown::closed()` is `Shown(false)` for symmetry. `ShownFollow::closed()` is `(ShownFollow, StartsClosed)`: `StartsClosed` is a one-shot marker whose `on_add` hook closes the node and takes itself off, and `ShownFollow` has its own `on_add` hook that closes a node whose host already wrote `Display::None`. Tests do not run a frame: `a_node_spawned_with_shown_false_is_closed_before_any_frame_runs` reads the world straight after the spawn (closed, hidden, no size on the first frame, no Tab stop) and `shown_follow_closed_spawns_a_closed_node_the_host_can_open` (the host opens it by writing `display`). **The one-frame lag** of `ShownFollow` is documented: `follow_display` runs in Style, so a host that writes `display` before it follows the same frame and one that writes after it (or in `PostUpdate`) follows a frame later.
   G-88 review notes: `FollowMemory` can no longer be stale: opening restores the remembered visibility only if the node is still the `Hidden` that was written, and a visibility the host set while it was closed is kept (`a_visibility_the_host_set_while_closed_is_kept_when_it_opens`); a `ScrollGutter` that is not a number falls back to the default lane, not a 0 px lane (`a_nan_scroll_gutter_falls_back_to_the_default_lane`).
3. **A node whose `display` and `height` the host writes: confirmed, nothing fought.** `ShownFollow` (display) with `HostGeometry` and a `Sizing { height }` (lengths) on one node keeps the host's `height` and `display` through a skin change, with colour motion off and on, and the visibility follows (`a_node_with_the_hosts_display_and_height_keeps_both_through_a_skin_change`: three alternating host writes, each with a skin change and 30 frames). A `terminal_view` row whose height is written every frame is the same node without `ShownFollow`.
2. **`scroll_region` follows focus and pages.** A `ScrollGutter` viewport is now one of the viewports `scroll_to_focus` and `page_lists` know (`Viewport` includes it; the region is not itself a paging candidate), so Tab, the arrows and PageUp/PageDown move focus and the scroll follows, glide included; the new `scroll_region_ends` (Navigate, same run conditions as paging) answers Home and End by focusing the first or last widget of the region, unless the focused widget keeps those keys (slider, choice, binding, divider, tab, text field, number part). The rail stays (`a_scroll_region_follows_keyboard_focus_into_view`: twelve real Tab presses, the focused row in view, the rail `ListRail` and shown; `a_scroll_region_answers_page_home_and_end_with_real_keys`).
4. **A host-managed scroll pane: documented and tested.** Put the host's rows in the region's items column and replace them there in one command flush: `ScrollPosition` is the viewport's, so the offset survives eight frames of full replacement, and what is drawn stays scrolled (`a_scroll_view_whose_children_the_host_replaces_every_frame_keeps_its_offset`). The pattern is in the `scroll_region` rustdoc.
