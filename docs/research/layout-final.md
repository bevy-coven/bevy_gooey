# What was left of the editor's hand-built nodes after G-86

Researched 2026-11-14 for issue #98 (G-87), asked by bevy_dark_factory (the Cauldron), #260 (UI-99), tracking #208. After the editor adopted G-84 to G-86 its raw `Node` literals and hand patches went from 230 to 80; what was left that gooey can solve is here. Each item is a general need; the editor is the example and its name is in no API.

## Method

The rules of G-84 (`docs/research/layout-gaps.md`) stand: a layout choice is data on the node, never a literal in the host and never a number in `apply_skin`; the constructor or component puts it on the node and `apply_skin` writes the `Node`, so it follows the skin and the player's text size. G-84's review added one: **every field is an `Option`, and a field left `None` leaves the node alone** (`RowLayout`), so a component sets only what it names and never resets what a role or a host gave. Components that set a size, a space or a shape go on any node with a `Role`; where a unit is needed it is the skin's own (a step of `GooeySkin::spacing`, a multiple of the line weight `GooeySkin::border`, a step of `GooeySkin::radii`). Pointer defaults are documented on each constructor (a mark or a gap is `Pickable::IGNORE` like `screen()`).

## Items
1. **A border whose colour the host paints by state: `InkFollow`.** `InkOverride { edge }` pins one colour; the editor's chips, buttons, list rows and quiet rows paint their edge by state (held, selected, hovered, failing) from their own systems. The issue offered (a) a state map inside `InkOverride` or (b) an `InkFollow` marker, the colour twin of `HostGeometry`, and preferred (b) if cheaper. It is the cheaper and the more general: a state map would have to name every state the host can invent, where the host already owns the colour systems. `InkFollow` is a unit marker: `apply_skin` writes **neither the `BackgroundColor` nor the `BorderColor`** of such a node, whatever its role, state, `Shape` or `InkOverride` and whatever skin change restyles it, and still writes every other field (size, border width, radius, padding, text colour, overflow). A node spawned without colours is therefore transparent until the host paints it. It has a change trigger in both directions: adding leaves the colours as they are; removing restyles the node in the same frame (`RemovedComponents<InkFollow>` joins the nested removal tuple) so the skin paints it again (`ink_follow_beats_an_override_and_removing_it_restyles`, `an_ink_follow_node_keeps_the_hosts_fill_and_edge_and_the_skin_writes_the_rest`). A state-mapped override was not built: nothing here it would serve that `InkFollow` cannot.
3. **`RowLayout` and `LayoutGap` on container roles.** The missing-project and unreadable-map cards, the launcher's sidebar and page nodes, `game_ui_preview`'s panel with its own gap and padding and the terminal dock split were `Role::Card`/`Surface`/`Panel` nodes that were also flows. `RowLayout` (direction, align, justify, wrap, shrink) is now honoured on `Panel`, `Surface`, `Card`, `Tone`, `Menu`, `SectionBody`, `Screen` and a `sized` box besides the roles it had (`Row`, `Column`, `ButtonRow`, `FillColumn`, `FillRegion`, `Placed`, `Button`); **not** on a `Dock` or a `DockBody` (the dock writes their grid), a `Split` and its panes, a table, a list or a text. The list is `takes_a_row_layout` in `skin.rs` and the `RowLayout` rustdoc. The gap the issue asked for is a `LayoutGap` beside it (`RowLayout` has no gap field, one place for each value): on every one of those roles that is not a row or a column it writes `row_gap` and `column_gap` as that multiple of the skin's gap, replacing the role's own (a panel's `skin.gap` rhythm); without one the role keeps its own (`a_layout_gap_on_a_panel_replaces_its_own_row_gap`, `a_row_layout_applies_to_the_container_roles`, `a_panel_can_be_a_row_with_its_own_gap`, `a_changed_layout_gap_and_row_layout_restyle_a_panel`).
2. **A gap on a placed node.** The badge clusters and the badge row are placed nodes that are also flows. `Role::Placed` already took a `RowLayout` (G-85); it now takes a `LayoutGap` too, beside its `PlacedAt`, which keeps owning its place: the insets and the flow are separate fields, so they never compete (`a_placed_node_can_be_a_flow_with_a_gap_beside_its_place`).
4. **A layer that blocks the pointer: `scrim()`**, `Role::Backdrop`. The editor's modal layer was raw because it must block input. `scrim()` is a full-size layer over its host (absolute at 0 on every side), filled with `GooeySkin::scrim`, what it holds centred, with Bevy's default `Pickable` that **blocks**: over it the world under it is not hovered, where `cover()` is `Pickable::IGNORE` and is never hit (`a_scrim_blocks_the_pointer_and_a_cover_does_not`, a real pointer move and the `HoverMap`). It is not a `dialog()`: no focus trap and no Escape (a new `Role`, not `Role::Scrim`, which the dialog logic reads), the plain layer a host that handles those itself needs. Hideable with `Shown`: a hidden scrim is not hit and its children keep no tab stop, and shown it blocks again (`a_hidden_scrim_is_not_hit_and_a_shown_one_traps_no_focus`); its colour is the skin's, replaced by an `InkOverride` or `InkFollow` (`a_scrim_is_the_skins_colour_full_size_and_centres_its_child`). It takes a `RowLayout` and a `LayoutGap` like the other containers.
6. **Per-site leftovers**, one by one: (a) **`ui.rs`'s `SelectedRail`**, whose colour system queries `Without<Role>`: a gooey node always has a `Role` (that is how the skin sizes it), so the rail is `(placed_at(..), Sizing { width, height }, InkFollow)` and the colour system's handle is **`With<InkFollow>`** in place of `Without<Role>`; the skin sizes it and never paints it (`a_rail_is_a_placed_sizing_and_ink_follow_found_by_the_marker`). (b) **`toolbar.rs`' computed margin** is `Space::Px(computed)` written from a system into `Spacing::margin` (`a_computed_margin_is_a_px_space_written_by_a_system`); it restyles the node when it changes, so write it only when it differs. (c) **`compose.rs`' slot-label `display`**, written by `place_labels`: insert or change **`Shown`** on the placed label instead of writing `Node::display` (`a_placed_world_label_is_hidden_and_shown_with_shown`, with a `WorldAnchor` on it; the anchor owns the node's place and `Visibility` each frame and `Shown`'s `Display::None` hides it either way). (d) **`files.rs`' list row** is `list_row()` with `InkFollow` if the editor paints it (G-85, this issue's item 1). (e) **`editor.rs`' receipt row, a least height that follows the text size** (`LinesRoom`): **`Extent::Lines(n)`**, `n` times the skin's list-line height (1.2 body text sizes, the height a list row's text is given), so `Sizing { min_height: Some(Extent::Lines(2.0)), .. }` grows with the player's text scale (`an_extent_in_lines_follows_the_text_scale`, `lines_are_finite_checked_and_never_negative`).
5. **The frame and the chrome.** Mapped piece by piece before anything was built (posted on #98 first; the table is below). **One gap, built: `GapPx(f32)`**, a gap between a container's children in **logical px**, where `LayoutGap` is a multiple of the skin's gap: the bars' `GAP_GROUP` and the door strip's 2 px are the host's own tokens. It is written as both `row_gap` and `column_gap` on a row, a column, a button row, a `fill_column`, a `fill_region` and the containers that take a `LayoutGap` (a panel, a surface, a card, a placed cluster), wins over a `LayoutGap`, including the gap between the lines of a wrapping flow, is finite-checked (not a number leaves the role's own, below zero is none) and has a `Changed` trigger (`a_gap_px_is_that_many_px_between_children`, `a_gap_px_beats_a_layout_gap_is_finite_checked_and_restyles`, which flips it after spawn). Everything else is gooey's own parts: `the_frame_is_built_from_gooey_parts_and_lets_the_pointer_through` lays the whole frame out for real (a window-sized root with `Extent::Vh`, a bar and a door strip with px gaps, padding, a one-sided `BorderPx` and `InkFollow`, a body of a dock, a viewport that takes the rest and a dock hidden with `Shown`, a status band) and shows that with `Pickable::IGNORE` on each container the pointer reaches the world under the bar, the body and the band.

The mapping: (worker `g87` on bmb, branch `fleet/g87`). Read from `crates/bevy_cauldron/src/chrome.rs` (`spawn_frame`, `panel_root`, `text_field`, `chip`, the name box, the status band). Items 1-4 and 6 are on the branch: `InkFollow`, `RowLayout`/`LayoutGap` on container roles and placed nodes, `scrim()`, `Extent::Lines`.

## Review notes (the first cut of G-87)

- **`InkFollow` and colour motion.** `update_color_motion` runs on every `Role` + `ColorTrack` node and treats any new `BackgroundColor`/`BorderColor` value as "a new colour from the skin, the widget or the game": it springs to it. So with motion on a host's per-state paint on an `InkFollow` node was eased, contradicting "the host owns fill and edge". The motion system now lands the background and border lanes of a node that carries `InkFollow` (`Has<InkFollow>` in its query; the value the host writes is the value shown on the next frame) and keeps the text and icon lanes (the skin still draws those). Taking the marker off leaves no easing state: the lanes were landed on every frame, so the node eases from the colour it shows to the skin's. Tests with motion ON on a 60 Hz test clock: `with_motion_on_an_ink_follow_node_shows_the_colour_the_host_wrote_at_once` (fill and edge, four alternating writes, each equal on the next frame; a plain node eases the same write: the control) and `removing_ink_follow_with_motion_on_eases_from_the_shown_colour_to_the_skins`.
- **`InkFollow` and keyboard focus.** A button's focus ring is its border colour, so on an `InkFollow` node the host paints the ring (the skin writes none): `the_skin_writes_no_focus_ring_on_an_ink_follow_button`, in the `InkFollow` docs.
- **`scrim()` blocks the pointer only.** It is no dialog: Tab still reaches the controls beneath (`a_shown_scrim_does_not_trap_tab`); a focus trap is the host's, or a `dialog()`.
- **`GapPx` and `LayoutGap` on a `button_box`.** `Role::Button` now takes both (`takes_a_gap`), like `RowLayout` since G-86: `a_button_box_takes_a_gap_px_and_a_layout_gap`. A plain `button` carries neither component, so it keeps its own half-gap beside an icon.
