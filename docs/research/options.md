# Player options the crate owns: text size, interface size, controller buttons

Researched 2026-11-01 (iteration 20). No issue is open; this is the loop's own pick, the first slice of the log's "settings-screen kit": the rows an options screen shows for the settings **this crate itself reads** (`GooeySkin::text_scale`, `UiScaleSettings::scale`, `BindingSettings::pad_style`). A game's own settings (volume, difficulty) stay its own `slider`, `toggle` and `choice`; these three it cannot write for the crate, and each is seven or eight lines of the same wiring: a `choice`, its option strings, a step table, an observer that indexes the table, and a system that moves the row when the setting loads or changes. home-still's distill answered two searches ("game accessibility text size options subtitle size interface scale player setting", "Presentation Options change how the game is displayed text size contrast colour player needs") and `paper_search` one; the index holds the craft paper below and nothing on text size in shipped games, so the web sources are fetched copies (see `## Pending index`).

## Craft principle

Cairns et al. turn a catalogue of guidelines into one idea, "It further emerged in the analysis that all the guidelines could be framed as options, things that could be selected or not according to the particular needs and abilities of players", and file text size and the screen's scale under **Presentation Options** (their example of an interaction between options: "resolution of screen could make text too small"). They add the fact that makes a text-size row a feature for every game and not only an accessibility one: "disability does not define the audience. ... subtitles are only mentioned in GAG and Includification as ways to support players with hearing loss. However, in Beeston et al. (2018)'s sample of players, only 27 had any hearing impairment but 83 reported using subtitles". A player at a TV across a room, on a handheld or tired is the same player as one with low vision, and what serves them is a row in the options, not a build.

## How shipping games do it

Microsoft's XAG 101 asks for exactly the two things: "The best approach to ensuring that text is accessible for as many players as possible is by providing players with choices to configure the UI to best address their needs", and "Players should be able to resize text up to 200 percent of the minimum font sizes ... without the loss of content, functionality, or meaning", with the rule that the setting must reach everything the player reads: "Any adjustable text settings, such as increasing size, weight, and contrast, should carry over to all important text—this includes additional windows that overlay a UI, especially when key information like error messages are being displayed" (its examples are Grounded's delete-save dialog and Gears 5's subtitles). So a text size is one value that the dialog, the toast and the legend obey as well as the menu: the crate already does (`GooeySkin::text_scale` is read by every part), and the row only has to write it.

The Game Accessibility Guidelines separate the two sizes the way this crate does: "Although setting a good default size is beneficial, there isn't a single set size that everyone can read, due to differences in levels of visual impairments and differences in screen size or viewing distance", and for the whole interface, "some people prefer smaller UI elements that obscure less of the gameplay, so allowing it to be configurable means that both ends of the scale can be met." Their shipped example for the interface is *EVE Online UI scaling*: "UI scaleable up to 150%." So the interface size has steps below 100% as well as above, and its top is 150%; the text's top is 200%.

## Model adopted

- **C1. A row is a `choice`, and the setting is the resource.** `text_size(label)`, `interface_size(label)` and `pad_style(label)` each return the same bundle as `choice(label, options, selected)` plus one private marker component, so the row is Bevy's `Button`, one tab stop, steps with Left and Right, the D-pad and a click, and says each change once as `ValueChange<usize>` (`docs/research/choice.md`). The state is not kept twice: `GooeySkin::text_scale`, `UiScaleSettings::scale` and `BindingSettings::pad_style` are the one source of truth, and the row is a view and an editor of it. Buitinck et al.: "Sensible defaults ... one way to do a thing": a game spawns the row and does nothing else, and a game that wants other steps writes the 8 lines with `choice` itself.
- **C2. The player's step writes the one field.** A global observer per plugin (so each lives with the resource it writes: `GooeyStylePlugin` for the text size and the pad style, `GooeyScalePlugin` for the interface size) turns a `ValueChange<usize>` on a marked row into `skin.text_scale = TEXT_SIZE_STEPS[i]` and no other field, so a game's own skin survives. A step past the table is ignored.
- **C3. The resource moves the row, with no event.** One system per resource sets the row's `ChoiceValue` to the step nearest the resource's value (`model::nearest_step`: ties go to the lower step, a value that is not a number to the first). It runs when the resource changes and for a row spawned this frame, before `update_choices`, so a row never draws one frame at the wrong step and a loaded save, Shift+T in the gallery or another row's write all show on it. It sets the state with `set_if_neq` and sends no `ValueChange`, so nothing echoes and the game's observer hears only the player. A value between two steps (a game that set 1.1) shows the nearest step and is not rewritten until the player steps.
- **C4. The steps are tested sizes.** The text size offers 100%, 125%, 150% and 200% (XAG 101's top is 200%); WCAG says of a resize mechanism with steps in between, "authors must ensure that there is no loss of content or functionality at these incremental steps", so each step is a size `tests/large_text.rs` lays every widget out at and finds nothing left its box. The interface size offers 75%, 100%, 125% and 150% (both ends, EVE's 150% top). The controller offers `PadStyle`'s three, in its own order, named as the manufacturers do: "Xbox", "PlayStation", "Switch". Percent options are numerals and the controller names are proper nouns, so no row carries a string the host must localise; the label is the host's, like every widget's.
- **C5. The setting reaches everything on the same frame.** The row writes the resource in the observer, `apply_skin` and `scale_with_window` read it in `GooeySystems::Style` the same frame, so the heading, the rows (the row itself included) and every overlay grow before the next draw: the player sees what their step did while the ring is still on the row.

## Parameters

- `model::TEXT_SIZE_STEPS = [1.0, 1.25, 1.5, 2.0]`, `model::INTERFACE_SIZE_STEPS = [0.75, 1.0, 1.25, 1.5]`, the controller steps `[Xbox, PlayStation, Switch]`: design defaults from the sources above, not measured ones.
- Option strings: `format!("{:.0}%", step * 100.0)` for the two sizes; `Xbox`, `PlayStation`, `Switch` as `PadStyle`'s names.
- A row is a choice's size: 44 px at 720p, the height of a toggle (tests in `tests/choice.rs` hold it); no `GooeySkin` field is added.
- No new system runs at rest: each sync reads the resource's change flag and an `Added` filter over the rows.

## Validation targets

- Every step of the text row (100, 125, 150 and 200%): one panel holding a heading, a body line, buttons, a meter, a toggle, a choice, a slider, two binding rows, a text input, tabs over three pages and a list, and the overlays (the dialog, a toast, the legend), has no child more than 1 px outside its parent, in a window tall enough that nothing is cut by the window. A negative control (the panel squeezed to 300 px) reports 15 escapes, so the check can fail (throwaway, run once this pass).
- A player's step writes exactly one field: stepping the text row to 150% leaves every other `GooeySkin` field, `UiScaleSettings::reference_short_side` and `BindingSettings`'s prompts byte-for-byte as they were; one step is one write.
- A value the game sets (a loaded 1.5, a resource replaced) shows on the row in the same frame and sends no `ValueChange`; a value between steps shows the nearest and is untouched; a row spawned over a loaded setting draws at that step on its first frame.
- The interface size row changes `UiScale` to the window's share times the step the frame it is stepped (1280x720: 1.25 at 125%), and the controller row turns a binding row's keycap from "A" to "Cross" and the legend's words with it.
- A disabled row does nothing; Left and Right never leave it (a choice's own tests); `UiFeedback` is the choice's.
- Idle: thirty frames after settling write no `GooeySkin`, `UiScaleSettings`, `BindingSettings`, `ChoiceValue` or `UiScale`.
- `model::nearest_step`: the exact step, the midpoint (ties to the lower), below the first, above the last, `NaN`, an empty table; tested without an app.
- Frame time: no change in the gallery's paired minimum (the new code is observers and change-gated systems; the gallery does not spawn the rows).

## What great looks like

An options page that reads like a console's: **Text size**, **Interface size** and **Controller** as three rows of one family, the ring on the row the player is on. Right on Text size and the whole screen, the heading, the rows and the row itself, is bigger the same frame; at 200% in a 720p window an options panel of this size still sits inside the window with its legend clear of it; Right on Controller and a binding row's keycap says "Cross" instead of "A" at once. Nothing the player did not touch moves except by growing, and Left puts it all back.

## Deviations

- XAG 101 measures the 200% from the *minimum default* size (26 px at 1080p on a console). This crate's default is 20 px at 720p (30 px at 1080p), 15% above that minimum, so 200% here is 60 px at 1080p. A design default; the steps are a tested subset of what `text_scale` accepts, not its limit (a game may set any value; `problems()` still demands a finite one above zero).
- The text row is a stepper, not a slider: WCAG's rule is per step ("at these incremental steps"), a continuous value has no finite set to test, and a stepper shows the player the sizes the game was checked at. Not adopted: font face, weight, letter and word spacing and case (XAG 101's other aspects of text display), a high-contrast preset (Game Accessibility Guidelines asks "a choice of text colour, low/high contrast as a minimum"; a skin is the game's and `GooeySkin::problems()` checks it), and a reset-to-default mark.
- A row of a plugin the host left out (`interface_size` without `GooeyScalePlugin`) steps and does nothing: its observer and sync are that plugin's. A design default, documented in the rustdoc.
- The controller row sets the style the host will show; the crate still does not detect a pad's make (`docs/research/binding.md`), so the default stays Xbox.
